# CORE ARCHITECTURE: HTML TEMPLATE + VARS (IMPORTANT)
Every invitation is stored as THREE separate things in PostgreSQL:
1. `html_template` (TEXT): the invitation markup with Mustache placeholders, generated by AI, sanitized and validated.
2. `vars` (JSONB): all content values (names, dates, venues, bank accounts, copy, image URLs, music).
3. `theme` (JSONB): design tokens (palette, fonts, mood), rendered as CSS custom properties.

The template contains NO real content. Content lives only in `vars`. Benefits: the user can edit any text or photo without calling the AI again, the same template can be re-rendered with new vars, and AI cost is paid once.

## Rendering pipeline (server-side, GET /{slug})
1. Load the row by slug (published only; owner may view preview).
2. Render `html_template` with `{ ...vars, guest: { name } }` using Mustache. Auto-escaping ON. Triple-mustache `{{{ }}}` and partials are forbidden and rejected by the validator.
3. Wrap in a fixed shell document: `<head>` with OG tags built from `vars.meta`, whitelisted Google Fonts from `theme.fonts`, a `<style>` block with `:root{--color-primary:...}` from `theme.palette`, then the body, then our first-party runtime script.
4. Cache the result per (slug, updated_at). Invalidate when vars/template/theme change.
- `guest.name` comes from `?to=`, is NOT stored, is length-limited (max 80 chars), and is escaped at render.

## Variable schema (versioned with `vars_schema_version`, validated by zod)
Use snake_case keys. Example shape:
```json
{
  "couple": {
    "bride": { "full_name": "", "nickname": "", "father": "", "mother": "", "father_deceased": false, "mother_deceased": false, "instagram_url": "", "photo_url": "" },
    "groom": { "...same fields..." : "" }
  },
  "cover": { "photo_url": "", "date_short": "10 . 10 . 26" },
  "events": [
    { "key": "akad", "title": "Akad Nikah", "date_label": "Sabtu, 10 Oktober 2026", "time_label": "10.00 WITA - Selesai",
      "venue_name": "", "address": "", "maps_url": "" }
  ],
  "countdown": { "target_iso": "2026-10-10T10:00:00+08:00", "calendar_url": "" },
  "gifts": { "enabled": true, "accounts": [ { "bank": "", "holder": "", "number": "", "logo_url": null } ],
             "address": { "text": "", "recipient": "", "phone": "" } },
  "gallery": [ { "url": "", "alt": "" } ],
  "quote": { "arabic": "", "translation": "", "source": "QS Ar-Rum 21" },
  "copy": { "opening_line": "", "closing_prayer": "", "gift_intro": "", "wish_intro": "", "footer": "" },
  "love_story": [ { "title": "", "text": "" } ],
  "music": { "enabled": false, "url": null, "title": null },
  "meta": { "og_title": "", "og_description": "", "og_image_url": "" }
}
```
- Repeating data uses Mustache sections (`{{#events}}...{{/events}}`); optional sections use `{{#gifts.enabled}}...{{/gifts.enabled}}`.
- The Arabic verse and its translation are fixed constants in the codebase, injected into `vars.quote`. The AI must never generate or alter religious text.
- RSVPs and wishes are NOT in vars. They are dynamic and loaded by the runtime from the API.

## Template contract (what the AI must output)
The AI writes full-page markup as an ordered list of `<section data-section="...">` blocks. Required section keys and their required placeholders:
- `cover`: `{{cover.photo_url}}`, both `{{couple.*.nickname}}`, `{{cover.date_short}}`, `{{guest.name}}`, a button with `data-action="open-invitation"`
- `opening`: `{{copy.opening_line}}`
- `quote`: `{{quote.arabic}}`, `{{quote.translation}}`, `{{quote.source}}`
- `couple`: bride and groom full_name, photo_url, father, mother, instagram_url
- `events`: a `{{#events}}` loop with title, date_label, time_label, venue_name, address, maps_url
- `countdown`: element with `data-countdown` and `data-countdown-target="{{countdown.target_iso}}"`, calendar link `{{countdown.calendar_url}}`
- `gift` (optional wrapper `{{#gifts.enabled}}`): loop over accounts with a `data-copy="{{number}}"` button, plus address block
- `rsvp`: `<form data-rsvp-form>` (fields: name, attendance, message) and `<div data-wishes-list>`
- `gallery`: `{{#gallery}}` loop with `data-lightbox` images
- `love_story`: `{{#love_story}}` loop
- `closing`: `{{copy.closing_prayer}}`, `{{copy.footer}}`
- `music` toggle (only if enabled): `<button data-music-toggle>`
The AI may freely design markup, class names, inline SVG ornaments, layouts, and scoped CSS in a single `<style>` block (all selectors prefixed with `.inv`). It may NOT write any JavaScript. All interactivity (open cover, countdown, copy, lightbox, RSVP submit, wishes pagination, music) comes from our first-party runtime (`/public/invitation-runtime.js`) via `data-*` hooks.

## Validation and sanitization (server, before saving ANY template)
1. Parse and check that every required section and placeholder exists, and no unknown placeholders (not in the vars schema) are used.
2. Reject triple-mustache, partials, and Mustache comments with code-like content.
3. Sanitize HTML with an allowlist: no `<script>`, `<iframe>`, `<object>`, `<embed>`, `<form action>` (other than `data-rsvp-form`), no `on*` attributes, no `javascript:` URLs. Allow only `data-*` hooks from our list.
4. Sanitize CSS: no `@import`, no `url()` pointing outside our storage domain or `data:` SVG, no `expression()`, no `position: fixed` covering the full viewport except the cover.
5. Enforce max size (e.g. 200 KB).
6. On failure: retry the AI up to 2 times with the validator errors in the prompt; then fall back to a built-in base template (see below) so the user always gets a result.
7. Serve invitations with a strict CSP: scripts only from self (nonce), images from our storage, fonts from Google Fonts only.

## Base template library (also used as AI few-shot examples and fallback)
Ship 3 hand-built, validated base templates in `/src/templates/` (e.g. `elegant-gold`, `floral-soft`, `minimal-modern`), each passing the same validator. The create form has an optional "Gaya yang diinginkan" selector (Elegan, Floral, Minimalis, "Biarkan AI memilih"). The AI uses the closest base as its starting point.

# USER FLOW

## 1. Landing page (logged out)
Hero with value prop, phone-mockup sample, primary "Mulai Sekarang" button, how-it-works (3 steps), sample result, pricing teaser, FAQ. "Mulai Sekarang" goes to Google login, then to /create.

## 2. Create form (/create, logged in)
- Couple: full names, nicknames, parents (with "Almarhum/Almarhumah" toggles), optional Instagram.
- Photos: cover (1), couple portraits (2), gallery (up to 12). Drag-and-drop, client-side compression, previews.
- Events: Akad Nikah and Resepsi (Resepsi optional): date, start, end or "Selesai", timezone (WIB/WITA/WIT), venue, address, Maps link.
- Gift (optional): up to 3 bank/e-wallet accounts, plus physical address, recipient, phone.
- Love story (optional): a few sentences from each side, or leave blank for an AI-written gentle story.
- Music (optional): upload MP3 (max 8 MB) or pick from a small royalty-free library.
- Style preference selector, and slug (live availability check, lowercase letters/numbers/hyphens, reserved words blocked).
- Button: "Buat Undangan dengan AI".

## 3. AI generation (server-side, 2 steps)
Step A (vision + text): input photos (resized) + form data. Output STRICT JSON validated by zod: `theme` (palette with WCAG AA contrast, fonts from a whitelist of Google Fonts, mood) and `copy` / `love_story` values. Palette derives from the dominant colors and mood of the photos.
Step B (text): input theme + base template example + the template contract + vars schema. Output `html_template` only. Run the validation pipeline above.
Persist `html_template`, `vars` (form data + copy + fixed constants merged), and `theme` in separate columns in one transaction. Log the run in `ai_generations`.

## 4. Preview mode (free, ONE generation per account)
- Enforced server-side via `ai_generations` count (unique constraint + transaction), not just UI.
- /preview/[id] is owner-only, renders the same pipeline with a diagonal "PREVIEW" watermark, RSVP/wishes disabled, share buttons locked.
- Sticky bar: "Suka hasilnya? Aktifkan undangan" and "Bayar & Publikasikan".
- No regeneration before payment. Editing vars is allowed only after payment.

## 5. Payment
- One-time payment per invitation (price from env, default Rp 99.000), Midtrans Snap, webhook with signature verification.
- On success: `is_paid=true`, `status='published'`, watermark removed, sharing/RSVP/wishes unlocked. Allow unlimited vars edits (re-render, no AI cost) and 2 extra regenerations (new template and/or theme).
- `orders` table: id, user_id, invitation_id, amount, status, midtrans_order_id.

## 6. Public invitation (/{slug})
Server-rendered through the pipeline above, noindex, OG tags from `vars.meta`, reserved slugs blocked. Music starts only after the user taps "Buka Undangan" (browser autoplay rules).

## 7. Sharing via WhatsApp (simple)
- Dashboard shows the link, "Salin Link", "Bagikan ke WhatsApp" (`https://wa.me/?text=<encoded>`), and Web Share API where available.
- Guest tool: type a name to get `/{slug}?to=Nama%20Tamu` with copy and WhatsApp buttons plus an editable Indonesian message template.
- Guest list: add guests one by one or import a CSV (columns: name, optional phone). The table shows a personalized link and a "Kirim via WhatsApp" button per row (uses `wa.me/<phone>?text=...` when a phone exists), plus a "sudah dikirim" checkbox. No WhatsApp Business API and no automatic blasting.

## 8. Dashboard (/dashboard)
List invitations and status. For published ones: link and sharing tools, guest list, RSVP summary (Hadir / Akan Hadir / Tidak Hadir), wishes with delete, and a vars editor (form-based, re-renders instantly, no AI call).

# DATA MODEL (PostgreSQL, snake_case, migrations in `/supabase/migrations`)
- `invitations`: id uuid pk, user_id uuid fk, slug citext unique, status text check in (draft, preview, published, archived), `html_template` text not null, `vars` jsonb not null, `theme` jsonb not null, template_version int, vars_schema_version int, is_paid bool default false, published_at timestamptz, created_at, updated_at. Constraints: `jsonb_typeof(vars)='object'`, `jsonb_typeof(theme)='object'`, `length(html_template) <= 200000`. Index on (user_id), unique on slug.
- `invitation_images`: id, invitation_id, url, role (cover|couple|gallery|music), sort_order.
- `guests`: id, invitation_id, name, phone null, sent bool default false, created_at.
- `rsvps`: id, invitation_id, name, attendance (hadir|akan_hadir|tidak_hadir), message, created_at.
- `ai_generations`: id, user_id, invitation_id, step, model, status, error, tokens_in, tokens_out, created_at.
- `orders`: as above.
- RLS: owners access only their rows; public can read published invitations only through the render route (service role), and insert RSVPs only through a rate-limited API route.
